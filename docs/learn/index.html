Chapter 1

What is Multica?

Multica is a task management platform — like Linear — with one structural difference that ripples through the entire codebase: AI agents are first-class teammates, not a bolted-on chatbot.

In a traditional tracker, the assignee of an issue is always a person. In Multica, the assignee is polymorphic: a person, an AI agent, or a whole squad of agents. Assign an issue to an agent and it doesn't just sit there — a real coding tool wakes up on a real machine, does the work in an isolated git worktree, and reports back in the issue's comment thread like any colleague would.

Toggle the board below to see what that one design decision changes:

Humans assign, humans execute, humans update statuses. The tool is a shared to-do list.

Architect's note. "Agents as teammates" is not a UI skin. It forces: a polymorphic assignee_type + assignee_id on issues, a task queue between the server and the machines that run agents, a daemon that executes work on your hardware, and a realtime layer so everyone watches the agent work live. Each of the next chapters is one of those consequences.

Why a daemon at all? Agents run real coding tools (Claude Code, Codex, …) that need your repos, your credentials, your toolchain. Multica keeps execution local-first: the server only coordinates; code and secrets never need to leave your machine. The daemon polls outward over HTTPS, so it works behind any firewall with zero network setup.

Chapter 5

State & Realtime

The frontend stays coherent across three apps and N tabs because of one strict rule: every piece of state has exactly one owner.

Server state → TanStack Query

Issues, agents, workspaces, inbox — anything fetched from the API lives in the Query cache, keyed by wsId. Switching workspace changes the key, so the right data appears with zero manual invalidation.

packages/core/issues/queries.ts · packages/core/api/client.ts:258 (ApiClient — every request flows through newRequest(), the most connected function in the codebase: 452 graph edges)

Client state → Zustand

Selections, filters, drafts, modal state. Stores live in packages/core/ so web and desktop share them. Server data is never copied into a store — two sources of truth always drift.

packages/core/platform/core-provider.tsx (wires API client, auth/workspace stores, WS, QueryClient)

An optimistic mutation, frame by frame

Multica never makes you wait for the server. Step through what happens when you change an issue's status:

WebSocket events invalidate — they never write

When anything changes server-side, the WS hub broadcasts an event like issue:updated or task:completed. The handler in packages/core/realtime/use-realtime-sync.ts does not patch stores with the payload. It marks the matching Query caches stale (debounced 100 ms per event prefix) and lets them refetch — the cache stays the single source of truth, and a dropped or replayed event can never corrupt state. On reconnect, every workspace-scoped cache is invalidated to recover whatever was missed (use-realtime-sync.ts:297).

One deliberate exception. task:message — the per-token stream while an agent is thinking — is written directly into its cache with setQueryData. Invalidating on every streamed message would flood the network with refetches. Exceptions are fine when they're chosen, named, and commented.

Chapter 6

The Daemon Up Close

The daemon is the bridge between "assignee: db-boy" in a database row and an actual CLI process editing files on your Mac.

Liveness: the heartbeat contract

Heartbeats ride the WebSocket; an HTTP fallback fires at 2× the interval so one dropped ack never flips you offline (server/internal/daemon/daemon.go:545). The server's 45s sweep marks silent runtimes offline; after 7 days they're pruned. A crashed daemon's tasks are rescued by runtime_recovery plus a 30s server-side scan.

Throughput: two concurrency gates

Tasks queue up; the daemon claims only what fits through both gates: 20 concurrent tasks per daemon (machine protection, MaxConcurrentTasks) and 6 per agent (a single runaway agent can't starve its teammates). Per-runtime pollers start at staggered offsets so a fleet of daemons doesn't stampede the server (daemon.go:1991).

Isolation: every task gets a fresh worktree

The daemon keeps one bare clone per repo (repocache/cache.go:68) and spawns a git worktree per task (cache.go:397). Two agents editing the same repo never touch each other's files; cleanup is instant; the bare clone makes the 2nd…Nth checkout nearly free.
